DEMO PRESENTER NOTES
====================

Goal of the demo
----------------
Use an AI agent to find inconsistencies between a Figma design and its
codebase implementation — in BOTH directions:
- things in Figma but missing in code,
- things in code but missing in Figma,
- mismatches in tokens, colors, spacing, radius, typography, sizes,
- layout differences (structure, order, alignment, gaps).

Output is a single self-contained HTML report (figma-code-audit.html) at
the repo root, with PNG previews + code snippets + diff tables side by
side, and explicit TODO blocks per mismatch. The agent also drops
one-line `TODO design-check:` comments in the codebase at each
inconsistency, posts `[design-check] ...` comments on the matching
Figma nodes via the REST API, and commits + pushes everything.


What we set up (and why)
------------------------

1. AGENTS.md (repo root)
   - Universal convention any AI agent reads on entry.
   - Defines THE TASK: what to compare, in which order, how to format
     the report, when to overwrite vs. append, what NOT to do
     (e.g. don't modify component code during a check).
   - This is the source of truth for the agent's behaviour. Everything
     else just points at it.

2. .github/prompts/design-check.prompt.md
   - VS Code prompt file → becomes the /design-check slash command in
     Copilot Chat (agent mode).
   - Just a trigger + step-by-step "how to start" that defers to
     AGENTS.md for the rules.
   - Optional convenience. You could also just type "run a design
     check" in chat.

3. .vscode/mcp.json
   - Wires up the Figma MCP server (figma-developer-mcp / Framelink)
     so the agent can read Figma data.
   - Reads the Figma token from .env (FIGMA_API_KEY).
   - Committed to the repo (no secrets in it). .env is gitignored.


Why MCP at all?
---------------
Without MCP, the agent would have to call the Figma REST API directly:
- responses are huge (multi-MB JSON for a single page),
- the agent must traverse styles, variables, component sets by hand,
- token budget gets eaten before any real comparison happens.

MCP gives the agent a TASK-SHAPED tool: "fetch this node, get a
simplified, style-resolved view." Less context, more signal.


Why this specific MCP server (Framelink figma-developer-mcp)?
-------------------------------------------------------------
- Returns a SIMPLIFIED, YAML-shaped view of frames with styles,
  variables, and component references already resolved — exactly what
  we need for "does this frame use the same tokens as the code".
- Has download_figma_images for visual sanity checks if needed.
- Uses a Figma personal access token (which you already have in .env);
  doesn't require the Figma desktop app to be running, unlike the
  official Dev Mode MCP.
- Mature, widely used, MIT licensed.


Why we did NOT add skills
-------------------------
Skills (SKILL.md) are packaged, reusable workflows surfaced to the
agent automatically when relevant. Useful when:
- the same workflow runs across many repos, OR
- you want auto-detection without an explicit slash command.

For ONE repo, ONE task, ONE trigger — AGENTS.md + the prompt file
already cover it. A skill would just be ceremony.


Why we did NOT add custom tools (other than the Figma MCP)
----------------------------------------------------------
The agent already has file read/search/edit built in, plus Figma via
the MCP. Nothing else is needed for this comparison.

If we later wanted to compare RENDERED screenshots vs. Figma exports,
a browser/visual MCP would make sense. Not needed for token/layout
diffs.


Why we did NOT add a GitHub Actions workflow
--------------------------------------------
We started to. The plan was: on push, run the agent in CI and commit
the updated report.

Blocker: workflow-driven AI runtimes (Claude Code Action) need a
separate paid LLM credential (ANTHROPIC_API_KEY). Our Copilot
subscription doesn't expose an API key from a workflow.

Alternatives kept open:
- Copilot coding agent (assign issues to @copilot) — pull, not push.
- Get an Anthropic key — cents per run, but separate billing.

For the demo we run it locally in VS Code only.


How the demo runs
-----------------
1. .env has FIGMA_API_KEY=... (Figma personal access token; needs the
   file_comments:write scope so the agent can post Figma comments).
2. Open repo in VS Code → MCP server starts automatically.
3. Open Copilot Chat → switch mode to "Agent". Make sure runInTerminal
   and createFile are enabled in the Tools picker.
4. Type /design-check and press Enter.
5. Agent:
   - reads AGENTS.md,
   - reads src/components/, src/tokens.css, src/pages/home/,
   - calls the figma MCP get_figma_data (root, then per node),
   - downloads PNGs to report-assets/,
   - compares components and layout,
   - writes figma-code-audit.html (overwrites any existing one),
   - drops TODO design-check: comments at mismatched code spots,
   - posts [design-check] ... comments on the matching Figma nodes,
   - commits and pushes everything.
6. Review the report; review the Figma comments; merge or revert as needed.


Key takeaways for the audience
------------------------------
- AGENTS.md is the universal "rules of the road" for any agent. Start
  there.
- MCP servers shape RAW data into TASK-SHAPED data. That's the whole
  point.
- Don't reach for skills/tools/CI by default. Add only when there's a
  concrete reason — otherwise it's overhead.
- Keep the report deterministic (same format every time) so it diffs
  cleanly in PRs.
